# Entities

The integration builds every entity from the vehicle's VIN. Entity IDs follow
`<platform>.xpeng_<vehicle>_<object_id>`, where `<vehicle>` is the last six
characters of the VIN — the same suffix the device name shows. Throughout this
page `<vehicle>` is written literally, e.g. `sensor.xpeng_<vehicle>_range`; on a
real car the placeholder is replaced by those six VIN characters.

The trailing `<object_id>` is generated by Home Assistant from the entity's
*English name*, not from the integration's internal `key=`, so the suffix is
usually the slugified friendly name — `sensor.xpeng_<vehicle>_tyre_pressure_front_left`
comes from `key="tyre_pressure_fl"`. `XPengEntity.suggested_object_id` pins the
suggestion to the English name so the id is the same in every UI language even
though the friendly name is translated; see [Translations](../guide/translations.md).
No entity is gated on model or trim in the code: a car that does not report a
field simply leaves that entity `unknown`.

The same entities, filtered to the integration, in Settings → Devices & Services → Entities:

Entity counts depend on the vehicle's capabilities, command policy and legacy
layout option. Existing entries keep legacy entities until the owner disables
**Keep legacy buttons and duplicate sensors**. New entries use compact mode.
Unknown optional hardware is not automatically declared unsupported.

## Compact controllers and climate modes

| Entity pattern | Type | State and behavior |
| --- | --- | --- |
| `cover.xpeng_<vehicle>_trunk` | cover | Measured trunk state; separate permissions for opening and closing |
| `cover.xpeng_<vehicle>_windows` | cover | Open means ventilation; close uses service 12; no arbitrary position/full-opening command |
| `cover.xpeng_<vehicle>_charge_port` | cover | Measured port state; motorized actions only when allowed/supported |
| `switch.xpeng_<vehicle>_charging` | switch | Measured charging state, explicit start/stop with acknowledgement checks |
| `switch.xpeng_<vehicle>_maximum_heating` / `_maximum_cooling` | switch | Capability-gated measured climate modes |
| `switch.xpeng_<vehicle>_<climate_mode>` | switch | Capability-gated measured Refresh, Sterilisation and A/C cleaning |
| `switch.xpeng_<vehicle>_<climate_mode>` | switch | Capability-gated measured rear defrost/Pet mode/Silent Mode; vehicle restrictions still apply |
| `sensor.xpeng_<vehicle>_hvac_fan_speed` | sensor | Raw fan telemetry retained in compact mode; fan-speed control remains withheld |
| `binary_sensor.xpeng_<vehicle>_climate` | binary sensor | Original evcc-compatible climate on/off interface retained with its existing unique ID |

Entity IDs above are defaults; renamed existing IDs are preserved. Front defrost
is exposed through the climate entity's preset. Legacy paired buttons and
duplicate sensors appear only when the legacy layout is enabled; the evcc
interfaces, raw fan reading and independent cabin measurements remain available.

## Charging history and energy

| Entity | Type | Unit | Notes |
| --- | --- | --- | --- |
| `sensor.xpeng_<vehicle>_last_charge_energy` | sensor | kWh | Energy taken by the last charge, rounded to 1 dp; device class `energy` but **no** state class (it is per-charge, not cumulative) |
| `sensor.xpeng_<vehicle>_last_charge_range_added` | sensor | km | `chargeStatistics.addedRange` |
| `sensor.xpeng_<vehicle>_last_charge_duration` | sensor | min | Source field is milliseconds; divided by 60,000 |
| `sensor.xpeng_<vehicle>_energy_consumption_7_day_avg` | sensor | kWh/100km | REST report, `avgTripEnergyPowerOf7Days`; also exposes `report_url` and `avg_7day_kwh_per_100km` |
| `sensor.xpeng_<vehicle>_parked_consumption` | sensor | kWh | Standby drain estimate; state class `total`, resets at local midnight, attributes `soc_drop_percent_today`, `yesterday_kwh`, `usable_battery_kwh`, `day`, `tracking` |

::: warning
`Energy consumption (7-day avg)` is **gated per account by XPENG**. A secondary
(shared) account is refused the underlying report and the endpoint returns
exactly `0.0` with no error, while the owner's app shows the real figure. A `0.0`
on this sensor must not be read as "no consumption" — when the value is `0.0` the
sensor adds a `zero_may_mean_restricted` attribute saying exactly that. Compare
against the owner account's app before trusting it.
:::

`Parked consumption` is a coarse estimate by design: XPENG reports SOC to whole
percent and pushes rarely while asleep, so each observed 1 % drop while parked
and not charging is converted with the configured usable pack size (the
`usable_battery_kwh` option, default 87.5 kWh — the G6 Long Range NMC pack; a G6
Standard Range LFP pack is about 66 kWh). Driving and charging are excluded.

## Remote commands

Every write path is either a `button` (stateless command) or one of the
optimistic control entities. Buttons send an MQTT command straight to the car
with no confirmation; the last response is visible on
`sensor.xpeng_<vehicle>_command_feedback`.

Each one exists **only as far as [Command permissions](../reference/command-permissions)
allows**: a group set to Disabled is not created at all, and one set to Read only keeps
its state but refuses its commands - so an entity listed below can legitimately be
missing. A new install starts at **Safe Plus**, which has everything here except the OTA
switch, the trunk-power outlet, unlocking, the trunk and the windows.

## Diagnostics

These entities answer "is the integration still receiving data?", which is not
the same question as "what is the car doing?" — a parked, asleep car produces no
messages, and that is normal. All of them are `EntityCategory.DIAGNOSTIC`
(`Credential age` and `Last data update` are the two exceptions: they are
uncategorised but diagnostic in purpose). The health entities poll themselves
every 30 s instead of waiting for a push, because their values keep changing
while nothing else happens.

| Entity | Type | Healthy value | Notes |
| --- | --- | --- | --- |
| `binary_sensor.xpeng_<vehicle>_credentials_valid` | binary_sensor (diagnostic) | `on`, attribute `reason: connected, no failures recorded` (or `reason: ok` when a fresh session is not up) | ON when the MQTT client has a **live session and no failure on record** — with mint-on-demand there are deliberately no recent mints to point at while connected — or, when disconnected, when a successful refresh is on record and no older than **3 × `mqtt_refresh_interval`** (135 s at the default 45 s) with no consecutive failures. OFF reasons: `no successful refresh yet` (never worked since start — points at onboarding), `N consecutive failures` (the broker refused), `no successful refresh for Ns` (stale). Other attributes: `last_success`, `age_s`, `stale_after_s`, `last_error`, `account`, `client_id`. The `client_id` is the install's device identity, truncated to its first 26 characters |
| `binary_sensor.xpeng_<vehicle>_mqtt_connected` | binary_sensor (diagnostic) | `on` | The paho session to XPENG's broker. Attributes `last_state_message_age_s` and `last_message_age_s`; a `0` there means either "arrived this second" **or** "nothing has arrived yet this session" — the code is explicit that those two are indistinguishable from the client's own clocks |
| `sensor.xpeng_<vehicle>_polling_status` | sensor (diagnostic) | `Parked` for a parked, quiet car; `Active` while charging or driving | The one-word answer. `Reconnecting` = socket down; `Silent` = nothing meaningful for 300 s with the socket up; `Escalated` = the watchdog has already sent a force-upload (only after 30 min of silence, at most once per 12 h, unless the last state said the car was moving — then it cannot be woken, so it is one per 10 min and one per episode of motion). Attributes: `cadence`, `mqtt_connected`, `seconds_since_data` (the one to watch — it resets only when a message carried data), `state_silence_seconds`, `any_msg_age_seconds`, `mqtt_query_interval_seconds`, `rest_poll_interval_seconds`, `last_query`, `escalations_this_session`, `last_query_at`, `last_rest_poll_at`, `last_escalation_at`, and `last_takeover_at` / `account_takeovers` when a renewal login has evicted the session |
| `sensor.xpeng_<vehicle>_next_poll` | sensor (diagnostic) | A future timestamp | `device_class: timestamp`. Attributes `query_interval_seconds`, `last_query`, `timer_started_at`, `counted_from`, `timer_granularity_seconds`, `next_rest_poll_at`, `seconds_to_next_rest_poll`. The due time is not the send time: the timer acts on its own cadence, which is what `timer_granularity_seconds` reports |
| `sensor.xpeng_<vehicle>_last_data_update` | sensor | A recent **timestamp** | `Last data update` in the UI (`key="last_update"`), `device_class: timestamp` — Home Assistant renders it in your timezone and can age it. A long age is normal for a sleeping car. Attributes `timestamp`, `age_seconds` kept for templates |
| `sensor.xpeng_<vehicle>_last_data_timestamp` | sensor (diagnostic) | The same instant | `device_class: timestamp`; `unknown` until the first vehicle message. It duplicates the row above (which was kept on its old entity ID for existing dashboards) — either works in automations. Note the entity ID ends in `_last_data_timestamp`, not `_last_data_update`, because object IDs come from names and `Last data update` already belongs to the sensor above |
| `sensor.xpeng_<vehicle>_mqtt_listener` | sensor (diagnostic) | `No messages` on a quiet car | Reports `<n> messages`, or `No messages` before anything arrives. Attributes `message_count`, `log` (rolling 50-event text log, ready for a Markdown card), `last_topic`, `last_payload`, `last_received` |
| `sensor.xpeng_<vehicle>_mqtt_discovery` | sensor (diagnostic) | `No discovery` until discovery is enabled and has run | Otherwise `<accepted> accepted / <rejected> rejected`. Attributes `accepted_topics`, `rejected_topics`, `results` |
| `sensor.xpeng_<vehicle>_command_feedback` | sensor (diagnostic) | `unknown` until a command is answered | The last MQTT command response: message text, else the numeric `code`, else `received`. Attributes `count`, `service_type`, `msg_type`, `code`, `message`, `msg_id`, `timestamp`, `recent` (last 5) |
| `sensor.xpeng_<vehicle>_last_notification` | sensor (diagnostic) | `unknown` until something new arrives | Fed by both rare `msg_type=3` MQTT frames and the app's server-side Message Centre, polled every `notification_poll_interval` (300 s by default). `count` stays at `0` until a *new* notification arrives — the first poll primes a baseline rather than replaying the inbox. **Account-takeover notices are not recorded here** (since 0.6.15): the renewal app's login produces one every ~100 min, and it drowned the real notifications. It is on `xpeng_account_takeover` and the `polling_status` attributes instead |
| `sensor.xpeng_<vehicle>_credential_age` | sensor | Small just after a reconnect; can climb while a session stays up | How long since a credential was last **minted**, e.g. `0m` / `1m`, or `Unknown`. Credentials are minted on demand, so a long-lived session legitimately has no recent mint and the age climbs; it resets at startup, on a reconnect that minted, and on a renewal import. That is why `credentials_valid` — which counts a live connection as evidence — is the health signal, not this age. Attributes `refreshed_at`, `age_seconds` |
| `sensor.xpeng_<vehicle>_last_renewal` | sensor (diagnostic) | A recent timestamp, or `unknown` before credentials have ever arrived | `device_class: timestamp`. When a token + tenant pair was last installed: a renewal by the app, the Repairs card, a reauth, or the flow the app drives on a first install. Stored in the config entry, so it survives a restart — and it is **not** `credential_age` above, which follows the on-demand MQTT credential mint. Attributes `refreshed_at`, `age_seconds` |
| `sensor.xpeng_<vehicle>_account` | sensor (diagnostic) | The account email | Which XPENG account the tokens belong to, read from the config entry. Falls back to the numeric account ID with an `email_unknown_reason` attribute for entries imported before the email was recorded. The address is shown in clear text and will therefore be stored by the recorder |

There is **no dedicated device-ID sensor**: the per-install device identity is
surfaced only as the truncated `client_id` attribute of *Credentials valid*.

## Ambiguities in the source

- `charge_rate` and `discharge_capacity` have no unit or device class in the
  code; only the raw MQTT field name defines them.
- `charge_schedule_start` / `charge_schedule_end` are passed through raw, with no
  declared format.
- `cdu_partition` (`cduAOrBFlag`) is deliberately undocumented — the class
  docstring says its semantics are not defined in the source.
- `sentinel_mode` and `x_guard_camera` are two binary sensors over one field
  (`soldier_camera_status`), so they can never disagree.
- `power_state` (`car_power_state`) has no value mapping in the code.
- Every name-bearing entity resolves its friendly name through a translation key
  now; `sentinel_switch`, `sentinel_sensitivity_control` and
  `trunk_power_timer_control` used to be dead strings because those classes set
  `_attr_name` directly, and the seat/button/cover tables passed a `name=`. The
  entity IDs are unchanged: they were always derived from the same English names
  that are now pinned by `XPengEntity.suggested_object_id`.
- HVAC schedule switches have appointment-derived entity IDs, so they are not
  stable across cars.
- No entity is gated on model or trim, and none is disabled by default; a field
  the car or the account does not provide simply reads `unknown`.
